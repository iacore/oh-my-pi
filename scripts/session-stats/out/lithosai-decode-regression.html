On 16 October the plain id was the fast one and -fast the slow one; today the order is reversed. A client-side measurement bias would shift both ids together, so the mapping from id to deployment appears to have changed on our side of your API.

How this was measured

  • Source of the daily figures: the agent harness logs per request its wall duration and time to first byte, with the usage block your API returns. No re-timing, no estimates.
  • Exclusions: branched transcripts are deduplicated by entry id; requests whose decode window is under 250 ms are dropped, since a single-chunk response makes duration − ttft meaningless; zero-output requests are dropped. 16,706 calls remain for this model id over the period.
  • Independent check: 28 October, a plain Python SSE client (no agent harness in the path) streamed 1,600-token completions straight from /v1/chat/completions and measured the rates in the last table. Your API reports cumulative completion_tokens_details.reasoning_tokens in every chunk, so token counts are yours, not counted locally.
  • Controls: the step shows up inside every decode-length bucket (0.25–1 s, 1–3 s, 3–10 s) and inside a fixed context band, the cached-prefix fraction is flat at 0.99 across the period, and the output-tokens ÷ total-duration figure falls in step with the decode figure.
What we would like to know
  • Did anything change on 24 October in how deepseek-ai/DeepSeek-V4.1-Flash is served — hardware, quantization, batch size, a new deployment, or a routing change between the -fast / -ultra ids and the plain one?
  • The pricing page still advertises 250+ tok/s/user for this model. The 24–26 October median was 246 tok/s, at or just below that figure, so is it now a ceiling rather than a floor?
  • Time to first token rose about 60% over the same days (1.66 s to 2.73 s) at identical prompt size and cache hit rate. Is that queueing, and is it expected to settle?
